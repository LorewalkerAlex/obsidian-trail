#### 5.8.2 Stable New Issue action and lifecycle capability

The header keeps one stable `+` slot across every Project lifecycle state. Its semantic meaning is always `New Issue`; capability changes whether it is enabled.

```text
Planned       + enabled
In Progress   + enabled
Completed     + disabled
Canceled      + disabled
```

A disabled `+` stays visible so the header does not reflow when Project lifecycle changes. Hover/focus may explain the unavailable capability, for example that the Project must be reopened before creating new Issues. Activating the disabled control does not silently reopen the Project or open a Composer.

When enabled, `+` invokes the **standard Issue creation surface**:

```text
Project Workspace +
-> Standard Issue Composer
-> current Project prefilled
-> Project relation remains editable before Create
```

Project Workspace does not define the Composer's modal geometry, property-control layout, validation presentation, or keyboard contract. #### 5.8.3 Lifecycle variants use one Page skeleton

The same Page frame is retained for all Project lifecycle states:

| Project lifecycle | Header `+` | List | Board | Normal execution |
| --- | --- | --- | --- | --- |
| Planned | enabled | yes | no | unavailable; planning/backlog work remains legal |
| In Progress | enabled | yes | yes | normal Issue workflow |
| Completed | disabled | yes | no | unavailable; settled review/correction only |
| Canceled | disabled | yes | no | unavailable; legal cleanup remains |

Lifecycle does not rewrite or hide actual current child facts. If a reopened/historical edge case leaves an Issue in a Status that is unusual for the Project lifecycle, List still shows the real Issue Status and only legal actions are offered.

Presentation capability changes follow:

```text
capability gained
-> expose the newly legal option
-> do not auto-activate it

capability lost
-> leave an impossible presentation
-> fall back to the nearest valid presentation
```

Therefore:

- Planned -> In Progress reveals Board but keeps the current List presentation;
- Completed/Canceled -> In Progress also reveals Board but does not auto-switch;
- if an In Progress Project leaves the Started lifecycle while Board is active, Project Workspace falls back to List;
- Filter state is preserved through that fallback.

Completed/Canceled do not receive a large lifecycle banner and the whole Main View is not globally muted. Terminal styling follows each Issue's own Status. An unresolved child Issue inside a Canceled Project remains visually actionable/attention-worthy rather than becoming gray merely because its parent Project is Canceled.

The enclosing section already supplies Status order. Terminal sections may suppress actionable Due emphasis; they still keep deterministic ordering and do not become an activity/history feed merely to surface recent completion.

- automatically switch to List because width changed;
- squeeze Cards until their scanning information becomes unreadable.

Column headers may remain sticky during long vertical scrolling. During drag, approaching the horizontal Board edge should auto-scroll the Board so an off-screen legal Status column can become a drop target.

#### 5.8.11 Filter and Board interaction

Filter and presentation are independent:

```text

-> current Filter
-> current presentation
```

Switching List/Board keeps the exact Filter. A Status Filter may contain Backlog/Canceled values even though Board has no corresponding columns. Board does not delete, disable, or rewrite those Filter values.

Filter affects Cards, not the workflow skeleton. Board always keeps its normal Todo/In Progress/Done columns even when one or more have zero matching Cards. Column count is the current visible/filter-matching Card count.

For example:

```text

```

Dragging a visible Todo Card into In Progress is legal when capability allows it. After Status changes, the Card naturally disappears because it no longer matches `Status - Todo`; no warning is required merely because a normal mutation changed Filter membership.

```text

Clear filters
```

This wording is intentionally Board-specific: matching Backlog/Canceled Issues may exist even while no Card can be rendered by the Board projection.

Peek is a transient floating surface inside the Main View. Peeking an Issue from Project Workspace does not replace the persistent Project Inspector target. Entering Issue Full Item changes the primary location and may show the Issue Inspector; host Back returns through normal Page history.

Project Workspace does not invent a separate selection grammar. Shared selection affordances remain distinct from ordinary Row/Card activation, so the Page does not depend on file-manager-style single-click-select/double-click-open behavior.

#### 5.8.14 Canceled Project unresolved attention

Canceled Project can legitimately retain unresolved child Issues. Main View does not add a large warning banner because the Status-first List already keeps unresolved In Progress/Todo/Backlog work at the top and shows the actual facts directly.

The already-resolved Project Inspector may expose a compact unresolved-work Attention signal. When its intended focus is exactly representable, activating it writes the normal Status Filter for unresolved categories rather than creating a hidden `unresolvedOnly` state.

```text
Main View
-> actual unresolved Issues remain visible/actionable

Project Inspector
-> compact derived attention/reason

Filter
-> normal focus mechanism
```

Terminal child Rows may be quieter, but unresolved child Rows are not globally muted merely because the parent Project is Canceled.

#### 5.8.15 Constrained Main View

Project Workspace follows these responsive priorities:

- preserve current Project identity before breadcrumb ancestry;
- allow description preview to compress before squeezing the collection;
- List progressively removes lower-priority Row metadata while preserving Title and important exception signals;
- Board keeps minimum useful Card/column width and scrolls horizontally inside the Board canvas;
- List never becomes Card layout merely because width is narrow;
- Board never auto-falls back to List merely because width is narrow;
- Project Inspector remains an Obsidian Right Sidebar concern and is not moved beneath Main View content.

Exact row/card dimensions, column minimums, sticky offsets, description clamp measurements, hover animation, and breakpoint values remain calibration details.
